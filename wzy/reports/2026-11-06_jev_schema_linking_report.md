# JEV + Text-to-SQL：短期实验结果（周五组会）

- 日期：2026-11-05 运行，2026-11-06 组会讨论
- 数据：BIRD mini-dev（SQLite），500 条，实际唯一 question_id 498 条（见 §8）
- 代码：师兄仓库 `tenghaha/jev-sql` 三个分支原样运行，未改任何代码；新增分析代码都在仓库外（见附录 B）

## 0. 结论摘要

1. 三个实验全部跑通，498 题无失败。列 F1：实验1 84.5，实验2 86.5，实验3 87.3（与师兄的 `evaluate_schema_linking.py` 输出逐位一致）。JEV 费用很低，单个实验全量估算约 0.2–0.3 美元，每题 3–5 秒。
2. **去掉 mention（实验2）比实验1 更好也更便宜**：列 F1 +2.0（95% CI [+1.1, +2.9]），列全召回率 +4.0，平均输入 token 从 15.3k 降到 9.7k，而且省掉一次 LLM 调用。原因是按 query 打分的列 Score 区分度更高（AUROC 0.984 vs 0.963）。
3. **模糊列二次判定（实验3）有小幅但显著的提升**：同一批 JEV 分数下，相对硬阈值 2.0，列 F1 +0.6 [+0.1, +1.1]，列 EM +4.8 [+2.4, +7.2]。JEV 重复调用的噪声只有约 ±0.1 F1，所以这个提升是真的。但二次判定拒掉的 734 列里有 284 列是 gold。
4. **最大瓶颈在表阶段**：实验2 有 14.7% 的题至少漏掉一张 gold 表，漏掉的 gold 列里 43% 是“表没选上”造成的，列阶段无法补救。表 Noul 本身区分度很好（AUROC 0.992，ECE 0.025），问题出在阈值 0.5 太严。补充实验 2b 把阈值降到 0.1：表全召回率 85.3% → 95.4%，列全召回率 +9.0 个点，但列精确率 −10.0、F1 −2.8，因为边缘表的列也被照常收进来。离线试的“表感知列阈值”能把 F1 拉回到与实验2 持平，同时保留 +5.7 个点的列全召回率（见 §4.1）。
5. **对论文定位最重要的一点**：qwen3.8-flash 一次调用直接选列，再套用同样的外键补全规则，列 F1 也是 87.3，和实验3 持平，token 只有 1/10。所以在 BIRD mini-dev 上“JEV 选列 F1 更高”这个说法不成立。JEV 的价值要从别处证明：可调的概率输出、校准（表级）、和 LLM 的互补（两者取并集，列全召回率从 62.2% 升到 71.3%）、以及大 schema 上的可扩展性。
6. 数据层面的注意点：46% 的 gold 列名直接出现在问题或 evidence 里（召回约 94%），其余列召回只有约 79%，真正难的是后者；412 道多表题里有 43 道的 gold 表在 schema 外键图中不连通，强制外键对它们无效。

## 3. 每个实验说明了什么

### 3.1 实验2 vs 实验1：去掉 mention

| 指标 | 实验2 − 实验1（百分点，95% CI） |
|---|---|
| 列 F1 | +2.0 [+1.1, +2.9] |
| 列 P / 列 R | +2.4 [+1.1, +3.7] / +1.7 [+0.5, +2.8] |
| 列全召回率 | +4.0 [+1.0, +7.0] |

- 按 query 打分的列 Score 区分度更高：列 Score 的 AUROC 实验1 0.963，实验2 0.984。
- 实验1 的规则是“任一 mention 与该列 Score ≥ 2.0 就入选”，mention 越多，误选机会越多。实验1 由 Score 入选的多余列 299 个，实验2 241 个。
- 三个难度档实验2 都不差于实验1（challenging：86.3 vs 83.9）。
- 结论：在 BIRD mini-dev 上，mention 抽取不值得保留。如果后面要用 mention，更合理的用法是做 value linking（把“EUR”对到具体值），而不是做列匹配的 span。

### 3.2 实验3 vs 实验2：模糊列二次判定

实验3 自己记录了步骤 2 的全部 Score，所以可以在**同一批分数**上比较不同规则，排除 JEV 调用波动：

| 规则（实验3 同一批分数） | 列 P | 列 R | 列 F1 | 列全召回率 | 平均列数 |
|---|---:|---:|---:|---:|---:|
| 实验3 实际（≥2.5 入选 + 带内二次判定） | 88.0 | 86.6 | 87.3 | 64.9 | 4.91 |
| 拒绝整个带（只保留 ≥2.5） | 90.2 | 81.5 | 85.6 | 52.6 | 4.51 |
| 硬阈值 2.0（实验2 的规则） | 87.3 | 86.0 | 86.6 | 62.4 | 4.92 |
| 接受整个带（保留 ≥1.0） | 76.2 | 90.5 | 82.7 | 75.5 | 5.93 |

- 相对硬阈值 2.0：列 F1 +0.6 [+0.1, +1.1]，列全召回率 +2.4 [+0.4, +4.4]，列 EM +4.8 [+2.4, +7.2]。提升不大，但显著，且多花约 0.9 s/题。
- 模糊带（1.0 ≤ Score < 2.5）很大：1284 列，分布在 427 题里，其中 56.2% 是 gold 列。
- 二次 Noul 在带内 AUROC 0.800。接受 550 列（gold 438），拒绝 734 列（gold 284），带内 gold 有 39% 被拒。
- 二次 Noul 阈值离线扫描：0.3–0.6 之间列 F1 几乎不变（86.9–87.3），列全召回率从 69.1% 降到 60.8%。如果下游更看重召回，把 0.5 降到 0.3 可以多拿约 4 个点的全召回。
- 二次判定的 prompt 写的是 “The column ... is only weakly related to the question. Is it necessary to add it ...”，先给了负面先验，可能让 JEV 偏向拒绝。建议做一个中性措辞的 A/B（这只是推测，未验证）。

### 3.3 JEV 重复调用的波动有多大

实验2 和实验3 的步骤 1/2 请求完全相同，两次运行的差就是 JEV 自身的波动：

- 表 Noul 平均绝对差 0.0061（最大 0.21），入选表集合 98.6% 一致。
- 15186 个共同列，列 Score 平均绝对差 0.021，Pearson r = 0.9989，在 2.0 阈值处翻转的只有 0.46%。
- 用实验2 的规则重算实验3 的记录，与实验2 的列 F1 差 +0.1 [-0.2, +0.4]。
- 结论：文档里说的“分值会随调用波动”确实存在，但很小。单次运行足以区分 1 个点以上的差异。

### 4.1 表阶段：阈值 0.5 太严

- 表 Noul 区分度和校准都很好（AUROC 0.992，ECE 0.025，Brier 0.026），但 0.5 的阈值会漏掉不少“半相关”的表。只要表没选上，它的列就不会进入打分。按入选表计算，列召回的上限只有 93.9%。
- 用实验2 记录的表 Noul 离线扫描（top-k = 5）：

| 表 Noul 阈值 | 表 R | 表全召回率 | 平均保留表数 |
|---:|---:|---:|---:|
| 0.5（当前） | 92.0 | 85.3 | 1.97 |
| 0.3 | 94.7 | 90.2 | 2.09 |
| 0.2 | 96.2 | 93.0 | 2.23 |
| 0.1 | 98.0 | 96.0 | 2.46 |
| 0（只按 top-5） | 99.8 | 99.6 | 4.60 |

- 新加进来的表没有列分数，离线扫描算不出列指标，所以补跑了 2b（表阈值 0.1）做端到端验证：

| 方法 | 列 P | 列 R | 列 F1 | 列全召回率 | 表全召回率 | 平均列数 | JEV token/题 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 实验2（表阈值 0.5） | 87.1 | 85.9 | 86.5 | 62.2 | 85.3 | 4.92 | 9724 |
| 2b（表阈值 0.1） | 77.1 | 91.5 | 83.7 | 71.3 | 95.4 | 5.92 | 11103 |
| 2b − 实验2（95% CI） | −10.0 [−11.7, −8.3] | +5.6 [+4.3, +7.0] | −2.8 [−3.9, −1.7] | +9.0 [+6.6, +11.6] | | | |

- 召回如预期大幅上升，但精确率掉了 10 个点。多出的错误主要来自新加进来的“边缘表”：由 Score 入选的多余列从 241 增到 452，只靠强制外键进来的多余列从 75 增到 223。原因是列阶段不知道这张表本身只是勉强入选，照样按 2.0 收列、照样强制外键。
- 在 2b 的记录上离线试了一个**表感知的列阈值**：表 Noul ≥ 0.5 的表仍用 Score ≥ 2.0；Noul < 0.5 的表，其列要 Score ≥ 2.75 才收；强制外键列只保留在仍有入选列的表里。结果列 F1 86.2、列全召回率 67.9%，F1 与实验2 基本持平（86.5），全召回率高 5.7 个点。这是在同一批记录上的探索性结果，没有算置信区间，需要正式重跑确认。
- 更一般的结论：表阶段和列阶段各自用独立阈值，组合起来不是最优的。表的置信度应该参与列的取舍，这本身也可以是方法的一部分。

### 4.2 列阶段：Score 是好的排序信号，但不是“相关等级”

各 Score 区间里 gold 列的比例（实验2）：

| Score 区间 | 列数 | gold 比例 |
|---|---:|---:|
| [0, 0.5) | 11488 | 0.3% |
| [0.5, 1.0) | 858 | 13.8% |
| [1.0, 1.5) | 451 | 38.6% |
| [1.5, 2.0) | 410 | 59.3% |
| [2.0, 2.5) | 434 | 73.0% |
| [2.5, 3.0] | 1570 | 92.1% |

- Score 在 1.5–2.0 之间时 gold 比例已经过半，按“≥2.0 才算 relevant”的字面意义设阈值偏保守。
- 实验2 列阈值离线扫描：阈值 1.5 → F1 85.3、全召回 67.9%；2.0 → 86.5 / 62.2%；2.5 → 85.4 / 52.6%。F1 在 1.5–2.5 之间变化不大，全召回率变化很大。阈值应该按下游需要的召回来定，不必追求 F1 最高。

### 4.3 外键元数据有缺口

412 道多表 gold 查询中，43 道（10.4%）的 gold 表在 schema 外键图里不连通，强制外键规则根本覆盖不到。两类原因（都核对过 gold SQL）：

- **兄弟表直接 join**：两张表各自有外键指向同一个父表，SQL 却直接互相 join。例：q12 `frpm.CDSCode = satscores.cds`（两者都指向 `schools.CDSCode`）；q197 `atom.molecule_id = bond.molecule_id`（都指向 `molecule`）。
- **元数据漏了外键**：例：q1030 `Match.league_id = League.id`，`dev_tables.json` 里没有这条（师兄文档 §12.3 也提到过）。
- 两类都可以用确定性规则补：从外键图推出兄弟连接，再按列名/类型匹配补漏掉的外键。不需要 JEV。

### 4.4 BIRD 的 evidence 把一半列名直接告诉了模型

- 2485 个 gold 列里有 1141 个（45.9%）的列名原样出现在问题或 evidence 中。实验2 对这部分召回 93.8%，对其余 1344 个只有 79.2%（qwen 不补外键时只有 39.0%）。
- 难点集中在“没被点名”的列：join 键、隐含的过滤条件、计数对象。
- evidence 是 BIRD 的人工标注，现实场景通常没有。论文里应同时报告有 / 无 evidence 两种设置。

## 5. JEV 的概率输出能不能直接用

GPT 对话里的判断是“confidence 不等于正确概率，必须先校准”。在这批数据上分三种情况：

| 输出 | 区分度（AUROC） | 是否接近真实概率 | 能否直接拿来做风险控制 |
|---|---:|---|---|
| 表级 Noul | 0.992 | 是，ECE 0.025（10 等宽分箱） | 基本可以，阈值可以按目标召回来定 |
| 列级 Score（期望等级 0–3） | 0.984 | 不是概率；Score 1.0–1.5 的列有 38.6% 是 gold | 需要先校准（如 isotonic 映射到概率） |
| 模糊带二次 Noul | 0.800 | 只在难样本上测过 | 区分度一般，适合作为级联里的一环 |

这里的 ECE 是在本数据集上测的，不代表 JEV 在其他任务上的校准水平。

## 6. 和“一次 LLM 调用”比，JEV 的价值在哪里

- qwen3.8-flash 直接选列时大量漏 join 键（列召回 63.9，列全召回率只有 17.9%），补上同一条外键规则后列 F1 87.3，和实验3 持平，且只用 1 次调用、约 1.1k token、0.8 s。
- 所以“JEV 做 schema linking 比 LLM 直接选列 F1 更高”在 BIRD mini-dev 上不成立。论文如果只讲 F1，审稿人会直接拿这个基线反驳。
- JEV 能拿出来的差异点：
  1. **可调的工作点**：JEV 给每张表、每列一个分数，阈值可以离线调，在召回和压缩之间任意取点；LLM 一次调用只有一个固定输出。
  2. **和 LLM 互补**：实验2 ∪ qwen+外键，列召回从 85.9 升到 90.8，列全召回率从 62.2% 升到 71.3%，代价是平均多 0.5 列。两者错的不是同一批列。
  3. **大 schema 的可扩展性**：mini-dev 最大的库只有 199 列，整库一次就能塞进 LLM（最长约 2.5k token），JEV 按表拆分的优势在这里体现不出来。要证明这一点得换 Spider 2.0 这类大 schema 数据集。
- 这和 GPT 对话里的判断一致：单纯做 schema 过滤创新性弱，“利用概率输出实现低风险 schema 压缩”更值得做。现在的数据支持这个方向：表级概率校准良好，列级区分度高但需要校准。

## 8. 下周建议（按投入产出排序）

1. **表阶段放宽 + 表感知列阈值一起改**：单独把表阈值降到 0.1 会掉精确率（2b：F1 −2.8）。要和“低置信表的列提高门槛、强制外键只留在活跃表”一起做，并正式重跑确认 §4.1 的离线结果。
2. **补外键候选**：从外键图推兄弟连接，再按列名/类型补漏掉的外键。确定性规则，工作量小。
3. **接下游 SQL 生成，测 EX**：schema linking 指标只是中间量，论文最终要看执行准确率。做法是用同一个生成器，分别给它全 schema、gold schema 和各方法选出的 schema，比较 EX。`analysis/sql_ex.py` 是我写的草稿，**尚未运行，也未验证**。
4. **列 Score 校准 + 按目标召回选阈值**：先用 isotonic 把 Score 映射成概率，再按“每题全召回率 ≥ 目标值”选阈值。这就是“低风险 schema 压缩”，可以借用 conformal risk control 的框架给出召回保证。
5. **三段式级联**：JEV 高分直接接受、低分直接拒绝，模糊带交给更强的模型或 qwen 复核，画成本–召回的 Pareto 曲线。实验3 的模糊带（56% 是 gold，二次 Noul AUROC 0.80）正好是这个级联的中间层。
6. **无 evidence 消融，以及大 schema 验证**：BIRD 的 evidence 点名了 46% 的 gold 列；JEV 按表拆分的优势只有在 Spider 2.0 这类大 schema 上才能体现。
