# JEV + Text-to-SQL：短期实验结果（周五组会）

- 日期：2026-11-05 运行，2026-11-06 组会讨论
- 数据：BIRD mini-dev（SQLite），500 条，实际唯一 question_id 498 条（见 §7 第 3 条）
- 代码：师兄仓库 `tenghaha/jev-sql` 三个分支原样运行，未改任何代码；新增分析代码都在 `wzy/` 目录下（fork 分支 `wzy/schema-linking-analysis`，见附录 B）

## 0. 结论摘要

**先看下游 EX（§3.4），它改变了怎么解读其余结论。** 用 qwen3.8-flash 按各方法选出的列写 SQL，在 496 道 gold 可执行的题上：直接给全 schema 的 EX 是 63.1；给 gold schema 是 71.6（+8.5 [+5.0, +11.9]）；**给 JEV 三个实验选出的列，EX 都比全 schema 低**（实验1 57.9、实验2 55.6、实验3 58.7，分别 −5.2、−7.5、−4.4 个点，置信区间都不含 0）。在当前阈值下，schema linking 不但没帮上生成，反而拖累了生成。原因是漏列：在漏掉 gold 列的题上，三组 EX 只有 35–38%。把 2b 的列阈值降到 0.5（每题平均 8.9 列，列全召回率 92.1%），EX 63.5，与全 schema 打平（+0.4 [−2.6, +3.4]），prompt 只有全 schema 的 1/4。gold schema 带来的 +8.5 说明压缩 schema 确实有空间，但目前的阈值都是按 F1 调出来的，选得太少。

1. 三个实验全部跑通，498 题无失败。列 F1：实验1 84.5，实验2 86.5，实验3 87.3（与师兄的 `evaluate_schema_linking.py` 输出逐位一致）。JEV 费用很低，单个实验全量估算约 0.2–0.3 美元，每题 3–5 秒。
2. **去掉 mention（实验2）在 schema linking 指标上更好也更便宜**：列 F1 +2.0（95% CI [+1.1, +2.9]），列全召回率 +4.0，平均输入 token 从 15.3k 降到 9.7k，而且省掉一次 LLM 调用。但下游 EX 实验2 反而比实验1 低 2.2 个点（[−4.6, +0.0]，边缘不显著）。换一次生成，实验2 的 EX 从 55.6 变成 57.3，所以 2 个点左右的 EX 差距落在生成噪声里，不能下结论。
3. **模糊列二次判定（实验3）在两类指标上都有提升**：同一批 JEV 分数下，相对硬阈值 2.0，列 F1 +0.6 [+0.1, +1.1]，列 EM +4.8 [+2.4, +7.2]；下游 EX 比实验2 高 3.0 [+0.6, +5.4]。但二次判定拒掉的 734 列里有 284 列是 gold。
4. **最大瓶颈在表阶段**：实验2 有 14.7% 的题至少漏掉一张 gold 表，漏掉的 gold 列里 43% 是“表没选上”造成的。表 Noul 区分度很好（AUROC 0.992，ECE 0.025），问题出在阈值 0.5 太严。2b 把表阈值降到 0.1：表全召回率 85.3% → 95.4%，列 F1 −2.8，但下游 EX +3.2 [+0.0, +6.7]。**F1 和 EX 给出的方向相反，以 EX 为准。**
5. **对论文定位最重要的一点**：qwen3.8-flash 一次调用选列再套用同样的外键补全，列 F1 87.3，下游 EX 60.9，都不比实验3 差（EX +2.2 [−1.0, +5.4]），token 只有 1/10。所以“JEV 选列比 LLM 准”这个说法在 BIRD mini-dev 上不成立。JEV 的价值要从别处证明：可调的概率输出（阈值放宽到 0.5 就追平全 schema，见 §3.4）、表级校准、和 LLM 互补（两者取并集，EX 比实验2 高 4.4 [+1.8, +7.3]），以及大 schema 上的可扩展性。
6. 数据层面的注意点：46% 的 gold 列名直接出现在问题或 evidence 里（召回约 94%），其余列召回只有约 79%，真正难的是后者；412 道多表题里有 43 道的 gold 表在 schema 外键图中不连通，强制外键对它们无效。

## 3. 每个实验说明了什么

### 3.1 实验2 vs 实验1：去掉 mention

| 指标 | 实验2 − 实验1（百分点，95% CI） |
|---|---|
| 列 F1 | +2.0 [+1.1, +2.9] |
| 列 P / 列 R | +2.4 [+1.1, +3.7] / +1.7 [+0.5, +2.8] |
| 列全召回率 | +4.0 [+1.0, +7.0] |

- 按 query 打分的列 Score 区分度更高：列 Score 的 AUROC 实验1 0.963，实验2 0.984。
- 实验1 的规则是“任一 mention 与该列 Score ≥ 2.0 就入选”，mention 越多，误选机会越多。实验1 由 Score 入选的多余列 299 个，实验2 241 个。
- 三个难度档实验2 都不差于实验1（challenging：86.3 vs 83.9）。
- 结论：在 BIRD mini-dev 上，mention 抽取不值得保留。如果后面要用 mention，更合理的用法是做 value linking（把“EUR”对到具体值），而不是做列匹配的 span。

### 3.2 实验3 vs 实验2：模糊列二次判定

实验3 自己记录了步骤 2 的全部 Score，所以可以在**同一批分数**上比较不同规则，排除 JEV 调用波动：

| 规则（实验3 同一批分数） | 列 P | 列 R | 列 F1 | 列全召回率 | 平均列数 |
|---|---:|---:|---:|---:|---:|
| 实验3 实际（≥2.5 入选 + 带内二次判定） | 88.0 | 86.6 | 87.3 | 64.9 | 4.91 |
| 拒绝整个带（只保留 ≥2.5） | 90.2 | 81.5 | 85.6 | 52.6 | 4.51 |
| 硬阈值 2.0（实验2 的规则） | 87.3 | 86.0 | 86.6 | 62.4 | 4.92 |
| 接受整个带（保留 ≥1.0） | 76.2 | 90.5 | 82.7 | 75.5 | 5.93 |

- 相对硬阈值 2.0：列 F1 +0.6 [+0.1, +1.1]，列全召回率 +2.4 [+0.4, +4.4]，列 EM +4.8 [+2.4, +7.2]。提升不大，但显著，且多花约 0.9 s/题。
- 模糊带（1.0 ≤ Score < 2.5）很大：1284 列，分布在 427 题里，其中 56.2% 是 gold 列。
- 二次 Noul 在带内 AUROC 0.800。接受 550 列（gold 438），拒绝 734 列（gold 284），带内 gold 有 39% 被拒。
- 二次 Noul 阈值离线扫描：0.3–0.6 之间列 F1 几乎不变（86.9–87.3），列全召回率从 69.1% 降到 60.8%。如果下游更看重召回，把 0.5 降到 0.3 可以多拿约 4 个点的全召回。
- 二次判定的 prompt 写的是 “The column ... is only weakly related to the question. Is it necessary to add it ...”，先给了负面先验，可能让 JEV 偏向拒绝。建议做一个中性措辞的 A/B（这只是推测，未验证）。

### 3.3 JEV 重复调用的波动有多大

实验2 和实验3 的步骤 1/2 请求完全相同，两次运行的差就是 JEV 自身的波动：

- 表 Noul 平均绝对差 0.0061（最大 0.21），入选表集合 98.6% 一致。
- 15186 个共同列，列 Score 平均绝对差 0.021，Pearson r = 0.9989，在 2.0 阈值处翻转的只有 0.46%。
- 用实验2 的规则重算实验3 的记录，与实验2 的列 F1 差 +0.1 [-0.2, +0.4]。
- 结论：文档里说的“分值会随调用波动”确实存在，但很小。单次运行足以区分 1 个点以上的差异。

### 3.4 下游 SQL 执行准确率（EX）

**做法**：同一个生成器（qwen3.8-flash，temperature 0，关闭思考，单次生成，不做自纠错或多候选），只改变它看到的 schema。schema 里只列出该方法保留的列（类型 + 一个样本值），以及两端都被保留的外键。按 BIRD 的规则比较结果集（行的集合），每条 SQL 30 秒、20 万行上限。498 题中有 2 题（q518、q701）的 gold SQL 本身在 30 秒内跑不完（q518 要 182 秒，q701 超过 600 秒），不计分，剩 496 题。脚本 `wzy/analysis/sql_ex.py`；全部生成请求在途峰值 5 个。

|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 全 schema（不做 linking） | 63.1 | 75.7 | 59.9 | 52.5 | 76.9 | 100 | 63.1 | - |
| gold schema（oracle） | 71.6 | 87.8 | 69.2 | 53.5 | 5.0 | 100 | 71.6 | - |
| 实验1 | 57.9 | 77.0 | 51.4 | 45.5 | 5.0 | 58.1 | 72.2 | 38.0 |
| 实验2 | 55.6 | 70.3 | 51.8 | 43.6 | 4.9 | 62.1 | 68.5 | 34.6 |
| 实验3 | 58.7 | 73.6 | 54.3 | 47.5 | 4.9 | 64.7 | 71.7 | 34.9 |
| 2b（表阈值 0.1，列阈值 2.0） | 58.9 | 70.9 | 56.7 | 46.5 | 5.9 | 71.2 | 66.0 | 41.3 |

| qwen 选列 + 外键补全 | 60.9 | 77.0 | 56.7 | 47.5 | 4.9 | 62.7 | 74.0 | 38.9 |
| 实验2 ∪ qwen+外键 | 60.1 | 73.6 | 56.3 | 49.5 | 5.4 | 71.2 | 67.4 | 42.0 |

**怎么读**

- **压缩 schema 有用，但要先召回够**。gold schema 比全 schema 高 8.5 个点，说明“少给无关列”确实能帮生成器。但三个实验在阈值 2.0 下只给约 5 列，35–42% 的题漏了 gold 列，漏列的题 EX 只有 35–38%，把压缩带来的收益全抵消了。
- **按 F1 调阈值是错的方向**。列阈值从 2.0 → 1.0 → 0.5，列 F1 下降（2b 记录上 83.7 → 78.8 → 69.9），EX 却上升（58.9 → 60.9 → 63.5）。下游生成器对多给几列很宽容，对少给一列很敏感。阈值应按“列全召回率”或直接按 EX 来选。
- **0.5 阈值只是追平全 schema，没有超过**。2b 列阈值 0.5 的 EX 63.5，与全 schema 63.1 打平，每题平均 8.9 列，prompt 约 247 token，全 schema 约 988 token。在 mini-dev 这种每库最多 199 列的小 schema 上，linking 的价值主要是省 token；EX 要超过全 schema，需要在不丢召回的前提下继续去掉无关列（gold 上限 +8.5 说明空间是有的）。
- **生成噪声和实验间差距是一个量级**。temperature 0 下，实验2 两次生成只有 301/498 题的 SQL 文本完全相同，26 题对错翻转，EX 差 1.6 个点。所以 2 个点左右的 EX 差距（如实验2 vs 实验1）不能下结论；3 个点以上、且置信区间不含 0 的（实验3 vs 实验2，各实验 vs 全 schema）才可信。正式报告时应多次生成取平均。
- gold schema 也不是满分：有 20 题全 schema 对、gold schema 错。看了其中 6 题，3 题是 BIRD 的 EX 判定对写法敏感：SELECT 列顺序不同（q50）、少了 `DISTINCT`（q220）、`RANK` 换成 `ROW_NUMBER`（q41）；1 题是生成器写了整数除法（q47）；另 2 题没细看。这类偶然差异也是小于 2 个点的 EX 比较不可靠的原因之一。

### 4.1 表阶段：阈值 0.5 太严

- 表 Noul 区分度和校准都很好（AUROC 0.992，ECE 0.025，Brier 0.026），但 0.5 的阈值会漏掉不少“半相关”的表。只要表没选上，它的列就不会进入打分。按入选表计算，列召回的上限只有 93.9%。
- 用实验2 记录的表 Noul 离线扫描（top-k = 5）：

| 表 Noul 阈值 | 表 R | 表全召回率 | 平均保留表数 |
|---:|---:|---:|---:|
| 0.5（当前） | 92.0 | 85.3 | 1.97 |
| 0.3 | 94.7 | 90.2 | 2.09 |
| 0.2 | 96.2 | 93.0 | 2.23 |
| 0.1 | 98.0 | 96.0 | 2.46 |
| 0（只按 top-5） | 99.8 | 99.6 | 4.60 |

- 新加进来的表没有列分数，离线扫描算不出列指标，所以补跑了 2b（表阈值 0.1）做端到端验证：

| 方法 | 列 P | 列 R | 列 F1 | 列全召回率 | 表全召回率 | 平均列数 | JEV token/题 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 实验2（表阈值 0.5） | 87.1 | 85.9 | 86.5 | 62.2 | 85.3 | 4.92 | 9724 |
| 2b（表阈值 0.1） | 77.1 | 91.5 | 83.7 | 71.3 | 95.4 | 5.92 | 11103 |
| 2b − 实验2（95% CI） | −10.0 [−11.7, −8.3] | +5.6 [+4.3, +7.0] | −2.8 [−3.9, −1.7] | +9.0 [+6.6, +11.6] | | | |

- 召回如预期大幅上升，但精确率掉了 10 个点。多出的错误主要来自新加进来的“边缘表”：由 Score 入选的多余列从 241 增到 452，只靠强制外键进来的多余列从 75 增到 223。原因是列阶段不知道这张表本身只是勉强入选，照样按 2.0 收列、照样强制外键。
- **但下游 EX 是上升的**：2b 比实验2 高 3.2 个点（§3.4）。多出的列对生成器的伤害很小，补回的 gold 列帮助更大。所以按 F1 判断 2b“变差”是错的。
- 在 2b 的记录上离线试了一个**表感知的列阈值**：表 Noul ≥ 0.5 的表仍用 Score ≥ 2.0；Noul < 0.5 的表，其列要 Score ≥ 2.75 才收；强制外键列只保留在仍有入选列的表里。结果列 F1 86.2、列全召回率 67.9%，F1 与实验2 基本持平（86.5），全召回率高 5.7 个点。这个规则的出发点是拉回 F1；有了 EX 结果之后看，它的全召回率比 2b 低 3.4 个点，下游未必更好，没有单独测 EX。
- 更一般的结论：表阶段和列阶段各自用独立阈值，组合起来不是最优的。表的置信度应该参与列的取舍，而且优化目标应该是下游 EX 或列全召回率，不是 F1。

### 4.2 列阶段：Score 是好的排序信号，但不是“相关等级”

各 Score 区间里 gold 列的比例（实验2）：

| Score 区间 | 列数 | gold 比例 |
|---|---:|---:|
| [0, 0.5) | 11488 | 0.3% |
| [0.5, 1.0) | 858 | 13.8% |
| [1.0, 1.5) | 451 | 38.6% |
| [1.5, 2.0) | 410 | 59.3% |
| [2.0, 2.5) | 434 | 73.0% |
| [2.5, 3.0] | 1570 | 92.1% |

- Score 在 1.5–2.0 之间时 gold 比例已经过半，按“≥2.0 才算 relevant”的字面意义设阈值偏保守。
- 实验2 列阈值离线扫描：阈值 1.5 → F1 85.3、全召回 67.9%；2.0 → 86.5 / 62.2%；2.5 → 85.4 / 52.6%。F1 在 1.5–2.5 之间变化不大，全召回率变化很大。§3.4 的 EX 结果证实了这一点：阈值应按下游需要的召回来定，在本设置下比 2.0 低得多（0.5 时才追平全 schema）。

### 4.3 外键元数据有缺口

412 道多表 gold 查询中，43 道（10.4%）的 gold 表在 schema 外键图里不连通，强制外键规则根本覆盖不到。两类原因（都核对过 gold SQL）：

- **兄弟表直接 join**：两张表各自有外键指向同一个父表，SQL 却直接互相 join。例：q12 `frpm.CDSCode = satscores.cds`（两者都指向 `schools.CDSCode`）；q197 `atom.molecule_id = bond.molecule_id`（都指向 `molecule`）。
- **元数据漏了外键**：例：q1030 `Match.league_id = League.id`，`dev_tables.json` 里没有这条（师兄文档 §12.3 也提到过）。
- 两类都可以用确定性规则补：从外键图推出兄弟连接，再按列名/类型匹配补漏掉的外键。不需要 JEV。

### 4.4 BIRD 的 evidence 把一半列名直接告诉了模型

- 2485 个 gold 列里有 1141 个（45.9%）的列名原样出现在问题或 evidence 中。实验2 对这部分召回 93.8%，对其余 1344 个只有 79.2%（qwen 不补外键时只有 39.0%）。
- 难点集中在“没被点名”的列：join 键、隐含的过滤条件、计数对象。
- evidence 是 BIRD 的人工标注，现实场景通常没有。论文里应同时报告有 / 无 evidence 两种设置。

## 5. JEV 的概率输出能不能直接用

GPT 对话里的判断是“confidence 不等于正确概率，必须先校准”。在这批数据上分三种情况：

| 输出 | 区分度（AUROC） | 是否接近真实概率 | 能否直接拿来做风险控制 |
|---|---:|---|---|
| 表级 Noul | 0.992 | 是，ECE 0.025（10 等宽分箱） | 基本可以，阈值可以按目标召回来定 |
| 列级 Score（期望等级 0–3） | 0.984 | 不是概率；Score 1.0–1.5 的列有 38.6% 是 gold | 需要先校准（如 isotonic 映射到概率） |
| 模糊带二次 Noul | 0.800 | 只在难样本上测过 | 区分度一般，适合作为级联里的一环 |

这里的 ECE 是在本数据集上测的，不代表 JEV 在其他任务上的校准水平。

## 6. 和“一次 LLM 调用”比，JEV 的价值在哪里

- qwen3.8-flash 直接选列时大量漏 join 键（列召回 63.9，列全召回率只有 17.9%），补上同一条外键规则后列 F1 87.3，和实验3 持平，下游 EX 60.9，也不比实验3 差（+2.2 [−1.0, +5.4]）。它只用 1 次调用、约 1.1k token、0.8 s。
- 所以“JEV 做 schema linking 比 LLM 直接选列更准”在 BIRD mini-dev 上不成立，无论按 F1 还是按 EX。论文如果只讲这两个数，审稿人会直接拿这个基线反驳。
- JEV 能拿出来的差异点：
  1. **可调的工作点**：JEV 给每张表、每列一个分数，阈值可以离线调，在召回和压缩之间任意取点；LLM 一次调用只有一个固定输出。§3.4 里正是靠把阈值从 2.0 调到 0.5，EX 才从 58.9 升到 63.5。LLM 的选列结果没法这样连续调。
  2. **和 LLM 互补**：实验2 ∪ qwen+外键，列全召回率从 62.2% 升到 71.3%，下游 EX 比实验2 高 4.4 [+1.8, +7.3]，代价是平均多 0.5 列。两者错的不是同一批列。
  3. **大 schema 的可扩展性**：mini-dev 最大的库只有 199 列，整库一次就能塞进 LLM（全 schema prompt 平均约 1k token），所以全 schema 本身就是强基线，JEV 按表拆分的优势在这里体现不出来。要证明这一点得换 Spider 2.0 这类大 schema 数据集。
- 这和 GPT 对话里的判断一致：单纯做 schema 过滤创新性弱，“利用概率输出实现低风险 schema 压缩”更值得做。现在的数据支持这个方向：表级概率校准良好，列级区分度高但需要校准；而 §3.4 说明，“低风险”要以下游 EX 不下降为准，不能以 F1 为准。

## 8. 下周建议（按投入产出排序）

1. **按下游 EX 重新选阈值**：表阈值 0.1、列阈值 0.5 已经追平全 schema（§3.4）。下一步在 BIRD train 上按库留出一部分调阈值，目标设成“列全召回率 ≥ 90% 时列数最少”，再在 mini-dev 上验证 EX。注意：本报告的阈值扫描都是在 mini-dev 上做的，属于在测试集上调参，只能作为方向参考。
2. **补外键候选**：从外键图推兄弟连接，再按列名/类型补漏掉的外键。确定性规则，工作量小。
3. **把 EX 做成多次生成**：生成噪声约 ±1.6 个点（§3.4），比较方法时每个设置至少生成 3 次取平均，或换用 self-consistency 等更稳定的生成方式。
4. **列 Score 校准 + 召回保证**：先用 isotonic 把 Score 映射成概率，再按“每题全召回率 ≥ 目标值”选阈值，可以借用 conformal risk control 的框架给出召回保证。这就是“低风险 schema 压缩”的方法核心。
5. **三段式级联**：JEV 高分直接接受、低分直接拒绝，模糊带交给更强的模型或 qwen 复核，画成本–EX 的 Pareto 曲线。实验3 的模糊带（56% 是 gold，二次 Noul AUROC 0.80）正好是这个级联的中间层。
6. **无 evidence 消融，以及大 schema 验证**：BIRD 的 evidence 点名了 46% 的 gold 列；JEV 按表拆分的优势只有在 Spider 2.0 这类全 schema 放不进 prompt 的数据集上才能体现。
7. **钉住 JEV 版本**（§7 第 4 条），以后的实验都用带版本号的模型 id。

## 9. 中长期调研

两份完整笔记在 `wzy/notes/`：`mid_term_jev_like_models.md`（约 550 行）和 `long_term_sql_template_generation.md`（约 460 行，附骨架统计脚本 `scripts/skeleton_stats.py`）。笔记里带数字的说法都附了来源链接，没能核实的标了“未核实”。下面只摘要点。我另外抽查了几条关键事实（见 9.3）。

### 9.1 中期：jev-like 开源决策模型和微调方法

- **关于 Jev 本身**：GPT 对话里引用的独立评测论文确实存在：Deußer 等（Bonn），arXiv 2609.37647，用 jev-1.13.0 在 37 个数据集上跑了 346,009 个请求。“1.14.0 还是预览版”一条已经过时，1.14 已在 2026-10-14 正式发布。
- **Bonn 发现的“多个 Noul 一起问会高估 yes”在我们的表阶段没有出现**：我们的表级 Noul 平均 P(yes) 0.286，实际正例率 0.284（§5）。所以对我们来说阈值应该往下调，不是往上调。这个反例本身可以写进论文。
- **合同限制**：TypeSafe 的客户协议第 2.3(b) 条禁止用 Jev 的输出做蒸馏或训练模仿模型。因此开源模型只能用 BIRD/Spider 的 gold 标签或开源 teacher 训练，不能拿 Jev 的概率当软标签。
- **建议先跑的 3 个开源对照**，分别代表三类方法：
  1. CodeS 的 schema item classifier（任务专用的有监督模型）；
  2. Qwen3-Reranker-4B 的 P(yes)（通用 reranker）；
  3. perplexity-ai/pplx-decider-flash-v1.2（据笔记，请求格式与 Jev 相同，只需换 `call_jev` 的传输层）。

  三者的推理都在单卡小时级（笔记里的估计）。
- **一个可以做成贡献的微调配方**：Qwen3-Reranker-4B + LoRA，用 BIRD23-train-filtered 和 Spider train 从 gold SQL 抽表/列，配同库 hard negatives；损失用 pointwise BCE 加表内 listwise CE；在按库切分的 dev 上做温度缩放和阈值选择。按 §3.4 的结论，阈值目标应设为列全召回率或下游 EX，不能用 F1。

### 9.2 长期：SQL 模板化生成，以及用 Jev 做端到端生成

- **经典方法**：“草图 + 槽位分类 + 确定性拼装”（SQLNet、SQLova 等）在单表 WikiSQL 上已经饱和；到了 Spider 的多表、嵌套查询，主流改成语法树解码或带约束的 seq2seq。LLM 时代的骨架/IR 主要用作示例检索键或生成的中间步骤，没有工作把“骨架 + 槽位”交给一个非生成式模型来决定。
- **mini-dev gold SQL 的骨架统计**（本地脚本，498 题）：
  - 子句级骨架高度集中：59 种，前 10 种覆盖 82.9%。完整的匿名 SQL 却是长尾：346 种里 304 种只出现一次。所以应该做“子句骨架分类 + 组合式槽位填充 + 确定性编译”，不能做整句模板库。
  - 按语法分层：扁平的选择/连接/聚合查询占 53.4%；加上算术、IIF/CASE、日期函数到 86.3%；再加单个子查询到 95.6%。挑战题这三档只有 26.5% / 75.5% / 92.2%。
  - 27.1% 的题含算术，但算术形式很集中，最常见的是百分比 `SUM(IIF(c,1,0))*100/COUNT(x)`；含算术的题有 91.1% 在 evidence 里直接给了公式。算术应由代码从 evidence 解析，Jev 只负责把操作数和条件绑定到列上。
- **误差累积是最大的硬约束**：每题中位约 10 个内容决策。即使每个决策准确率都是 0.98，整题全对率也只有约 67%，所以必须配 beam、执行过滤和低置信度时回退到 LLM 的门控。
- **推荐路线**：
  - 主线是“Jev-Sketch”：Jev 在一次请求里并行回答骨架、子句开关、SELECT/WHERE/GROUP/ORDER 槽位，sqlglot 确定性编译成 SQL，置信度低时回退 LLM。第一版语法覆盖约 78%。
  - 副线是“Jev 做候选 SQL 选择器”：2–3 天能出第一版结果。
  - 逐个语法产生式解码的方案不推荐：每题约 22 个节点、6–9 轮请求，太慢，而且已有大量同类工作。
- **新颖性**：已有一个 Jev 判槽 + sqlglot 编译的博客原型（Zenn，只演示了 3 个 TPC-H 案例，没有准确率统计），以及 SPC（LLM 规划 + 确定性编译，38 题）。检索中没有找到 Jev 在 BIRD/Spider 上的公开评测。
- **和本报告的关系**：§6 已经说明，不能预设“Jev 的离散决策比 LLM 准”。所以每个槽位都要和“LLM 在同一编译器下填同样的槽”逐一对比，论文卖点放在校准后的概率、可调工作点和成本上。
